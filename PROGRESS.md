**Dois bugs reais de deploy encontrados e corrigidos nesta sessão (não eram bugs de código até o segundo item)**:
1. `API_PORT=3001` (valor sugerido originalmente em `docs/production-deployment.md`) nunca fica "no ar" para o Render, porque o Render só varre um conjunto fixo de portas conhecidas (10000, 3000, 8000, 8080, 4567) para autodetecção — `3001` não está nessa lista, dando `No open ports detected`. Corrigido ajustando a env var no painel do Render (`API_PORT=10000`) **e** `docs/production-deployment.md` (já atualizado no commit `d70a935`, confirmado nesta sessão de continuação — a nota anterior aqui dizia que o arquivo ainda precisava de correção, mas isso ficou obsoleto).
2. **Bug real de código, corrigido** (`fix(web): replace API proxy rewrites() with a Route Handler`, commit `d478c10`): o proxy same-origin `/api/*` usava `rewrites()` do `next.config.ts` desde a Fase 4. Isso funciona em qualquer ambiente local/CI, mas a Vercel **bloqueia o destino de um `rewrites()` com o erro de plataforma `DNS_HOSTNAME_RESOLVED_PRIVATE`** quando o host de destino fica atrás de Cloudflare — o caso do domínio público do Render — mesmo com `API_INTERNAL_URL` correto e um build novo. Não é algo contornável por configuração: é uma checagem de segurança da própria camada de proxy da Vercel sobre o destino resolvido. Corrigido substituindo `rewrites()` por um Route Handler real (`apps/web/src/app/api/[...path]/route.ts`) que faz seu próprio `fetch()` contra `API_INTERNAL_URL` — código de aplicação normal, fora daquela checagem de plataforma, funcionando idêntico em dev/CI/produção, **incluindo o streaming SSE** de `/agent-runs/:id/events` (o `body` da resposta upstream é repassado direto, sem buffer — mesmo código path serve JSON normal e SSE, sem tratamento especial). `next.config.ts` não usa mais `rewrites()`; `API_INTERNAL_URL` agora é lido em runtime pelo Route Handler, não mais em build time — comentários atualizados em `playwright.config.ts`, `apps/api/test/otel-trace-propagation.e2e-spec.ts`, `README.md`, `docs/production-deployment.md`, `.env.example`, `.env.production.example` para não ficarem descrevendo o mecanismo antigo.
3. Antes desses dois: `db:migrate`/`db:seed` nunca tinham sido rodados contra o Neon real (erro `relation "users" does not exist`, PostgreSQL `42P01`) — resolvido rodando os dois comandos manualmente com `DATABASE_URL` exportado localmente. **Isto não é automático em nenhum deploy futuro** — se o Render recriar o banco (novo projeto Neon, branch de banco diferente, etc.), alguém precisa rodar migrate+seed de novo manualmente; não há hook de deploy fazendo isso hoje, decisão deliberada (ver `docs/production-deployment.md`, "Para uma primeira demo, o seed pode ser aceitável").

## Continuação da Fase 12 #4 — embeddings determinísticos locais + ranking semântico

Implementado nesta sessão, a partir da última pendência explícita da Fase 12 ("embeddings/vector store, ranking semântico"). Segue a mesma filosofia já estabelecida de infra local sem credenciais externas (PGlite/fila em memória/IA mock): um provider de embeddings determinístico e local por padrão, com a abstração pronta para um provider real (via API de um provider já existente — Gemini/Groq/Anthropic — ou outro) ser plugado depois por env var, análogo a `AI_PROVIDER`. **Nenhuma chamada de rede real a um provider de embeddings foi feita ou implementada nesta continuação.**

**`embedText` (`packages/knowledge/src/embedding.ts`, novo)**: embedding determinístico via "hashing trick"/feature hashing (a mesma técnica real por trás de `HashingVectorizer`/Vowpal Wabbit, não inventada aqui) — tokeniza o texto (mesma regra de termos já usada pela recuperação lexical, extraída para `splitTerms()` e reaproveitada por `retrieval.ts` em vez de duplicada), hasheia cada termo (SHA-256, `node:crypto`, sem rede) para escolher um índice + sinal (+1/-1) num vetor, acumula e normaliza por L2. Dimensão fixa em **256** — documentado no próprio código por quê (colisão baixa para os chunks/queries reais deste projeto, barato de guardar como `jsonb` e de comparar em memória sobre os poucos candidatos do fixture, sem precisar de índice vetorial dedicado). **Isto não é um embedding semântico real** — sinônimos verdadeiros (`erro`/`falha`) caem em índices diferentes e não são reconhecidos como relacionados; `embedding.test.ts` prova isso honestamente (um caso mostra que a similaridade "reconhecida" entre um par sinônimo só vem do resto da frase compartilhada, não do par em si — isolando as duas palavras, a similaridade cai a 0). O que a função captura de verdade é similaridade LEXICAL vetorizada (textos que compartilham/repetem termos ficam com cosseno alto), de forma determinística e sem custo.

**Persistência (`knowledge_chunks.embedding`)**: coluna nova, `jsonb` nullable com `$type<number[]>()` (`packages/database/src/schema/knowledge.ts`), migração gerada via `pnpm --filter @forge/database db:generate` (`drizzle/0005_nervous_piledriver.sql`, uma única `ALTER TABLE ... ADD COLUMN`). `jsonb` escolhido em vez de um tipo array nativo do Postgres (`real[]`): mesma convenção já usada em todo o resto deste schema para listas/estruturas (`allowedTools`/`labels`/`permissions`, `rules`/`scope`), suportado de forma idêntica por PGlite e Postgres real sem depender de extensão nenhuma (`pgvector` não foi adicionado, de propósito). O embedding é calculado uma única vez, dentro de `chunkKnowledge()` (`packages/knowledge/src/chunking.ts`, único funil real de chunking já reaproveitado por `indexKnowledgeFiles`/seed/reindex) — `persistIndexedKnowledgeSources` (`packages/database/src/knowledge-indexing.ts`) só grava `chunk.embedding` já pronto, nunca recalcula. Chunks/fixtures construídos manualmente sem esse campo (`PreparedKnowledgeChunk.embedding` é opcional) persistem `embedding: null`, sem erro.

**Ranking híbrido em `retrieveKnowledge()` (`packages/knowledge/src/retrieval.ts`)**: combina o score lexical já existente (contagem de termos da query encontrados, mantido como está — continua sendo o filtro real de inclusão, `chunk.score > 0`) com a similaridade de cosseno entre o embedding da query e o do chunk, numa média ponderada `hybridScore = 0.7 * (score / termosDaQuery) + 0.3 * max(0, cosseno)`. Pesos documentados no código: o lexical continua sendo o sinal PRIMÁRIO — decide se um chunk entra ou não no resultado, porque o hashing trick não entende sinonímia real; o semântico (peso menor) só refina a ORDEM entre candidatos que já bateram no filtro lexical, nunca traz para o resultado algo sem nenhuma correspondência exata de termo. Cosseno negativo é clampado em `0` (não existe noção de "sentido oposto" no hashing trick, só ruído de colisão — nunca deveria punir um chunk). Chunks sem embedding (legados, seedados antes desta coluna existir, ou nunca reindexados) recebem `semanticScore: 0` e caem para o score puramente lexical escalado, sem erro. **`score` (o campo já exposto pela API/UI) continua sendo o valor lexical bruto, inalterado** — `semanticScore`/`hybridScore` são campos novos e aditivos (`RetrievedKnowledgeChunk`, `KnowledgeSearchResult` em `apps/api`, `ApiKnowledgeSearchResult` em `apps/web`); a mudança real e observável desta continuação é a ORDEM dos resultados, não o valor exibido pela UI (que não foi tocada, por instrução explícita do escopo desta tarefa).

**Prova real e honesta de que o ranking melhora algo mensurável**: `packages/knowledge/src/knowledge.test.ts` tem um caso onde dois chunks empatam no score lexical (query de um único termo, presente nos dois) — um chunk concentra o conteúdo em torno do termo da query, o outro o menciona uma única vez em meio a dezenas de termos sem relação. Depois da normalização L2, a dimensão do hash daquele termo pesa proporcionalmente mais no vetor do chunk concentrado, gerando cosseno maior com a query — o ranking híbrido o coloca primeiro, mesmo com o score lexical idêntico (antes desta continuação, o desempate era só por ordem alfabética do título). Isso expôs um bug real de premissa num teste e2e pré-existente: `apps/api/test/knowledge-seed.e2e-spec.ts` assumia que "estornos" só existia no README do fixture (comentário do próprio teste) — falso, confirmado por grep: `src/lib/format-currency.ts`/`src/lib/invoice.ts` também mencionam "estornos" de verdade. Antes desta continuação, README.md sempre vencia esse empate por pura coincidência alfabética (`R` < `s`); com o ranking híbrido, o desempate passa a ser por similaridade real, e outro documento pode legitimamente vencer. Corrigido no próprio teste (comentário atualizado, assert deixou de fixar qual dos três vence o empate, passou a confirmar que o chunk do README está presente/correto/embrulhado E que a resposta inteira respeita `hybridScore` decrescente) — não uma correção que esconda ou reduza o que está sendo verificado, e sim uma correção de uma premissa que já era falsa antes desta sessão.

## Fase 17 — Fluxo de aprovação humana (detalhe)

Implementado nesta sessão: `POST /agent-runs/:id/approve` e `POST /agent-runs/:id/reject` (`apps/api/src/modules/agent-runs/agent-runs.controller.ts`/`.service.ts`), restritos a `agent_run:approve` (409 se a execução não estiver em `approval_required`, 404 genérico cross-tenant, mesmo padrão de `cancel`). Cada decisão: (1) transiciona o `agentRun` via `transitionAgentRunStatus` (`@forge/domain`) — aprovação vai para `completed`, rejeição para `failed`; (2) resolve toda `toolCall` que ficou `pending` aguardando aprovação para `succeeded`/`rejected` (`AgentRunsRepository.resolvePendingToolCalls`) — nenhuma fica "pendente" para sempre numa execução já terminal; (3) grava uma linha em `approvals` (reaproveitada, `subjectType: 'agent_run'`) via `AgentRunApprovalsRepository`, recuperando `requestedByUserId` do audit log `agent_run.triggered` mais recente para aquele `agentRun` (`AuditLogsService.findLatestActorForTarget`) — `null` se não existir; (4) publica no canal SSE existente (`AgentRunEventsService`); (5) grava audit log `agent_run.approved`/`agent_run.rejected`.

**Rejeição vai para `failed`, não `cancelled`** (decisão deliberada, ambas as arestas existem no grafo de `@forge/domain` a partir de `approval_required`): `cancelled` já tem semântica própria (interromper algo EM ANDAMENTO, `agent_run:cancel`, concedida a quase todo papel incluindo quem disparou a execução). Rejeitar uma proposta de uma execução que já rodou o pipeline inteiro (só parou por exigir aprovação) não é "interromper" nada — é um veredito sobre um resultado que já existe. Reaproveitar `cancelled` misturaria duas trilhas de auditoria/permissão distintas sob o mesmo status; a diferença real entre "falhou tecnicamente" e "foi rejeitada por um humano" fica na linha de `approvals` e no audit log, não no enum `AgentRunStatus`.

Frontend: `apps/web/src/app/(product)/projects/[id]/tasks/[taskId]/runs/[runId]/agent-run-detail-view.tsx` ganhou um painel "Aprovação necessária" (visível quando `status === 'approval_required'` e há tool calls pendentes) com os argumentos/resultado propostos e botões "Aprovar"/"Rejeitar" — só renderizados para quem tem `agent_run:approve` no cliente (`apps/web/src/lib/agent-run-approval-permission.ts`, mirror do RBAC do backend, mesmo padrão de `agent-run-cancelable.ts`; busca o papel via `GET /auth/me`, endpoint que já existia mas nunca tinha sido consumido pelo frontend). O backend é sempre a autorização real — o mirror só evita oferecer um botão que renderia 403.

Testes novos: `apps/api/test/agent-runs.e2e-spec.ts` (+9 casos: sucesso/409/403/404 para approve e reject, incluindo o teste do canal SSE), `apps/web/e2e/agent-run-approval.spec.ts` (3 cenários reais via Playwright: aprovar, rejeitar, esconder botões para `developer` — todos verificando a mudança de status via SSE, sem `page.reload()`). ## Fase 18 — Execução real (limitada) conectada atrás da aprovação humana

Implementado nesta sessão, na sequência direta da Fase 17: quando um `tech_lead`/`platform_engineer`/`admin` aprova uma execução parada em `approval_required`, toda tool call `write_file`/`apply_patch` que ficou `pending` agora **escreve de verdade**, não só muda de status.

**Fronteira de segurança (deliberada, releia antes de expandir isto)**:
- Só `write_file`/`apply_patch` viram execução real, e só contra uma **cópia isolada e descartável** do repositório demo — `.data/workspaces/<repositoryId>/` (`repositoryId` = PK de `repositories`, não `agentRuns.id`: a cópia é **persistente entre execuções sobre o mesmo projeto**, criada de forma preguiçosa na primeira escrita aprovada, para que um patch aprovado numa execução possa legitimamente desalinhar e falhar numa execução seguinte se o arquivo já mudou — é exatamente esse cenário que os testes cobrem). `fixtures/<repositoryName>/` original **nunca** é tocado — só lido uma vez, na cópia inicial (`fs.cp` recursivo, nunca sobrescreve a origem).
- `run_command`/`run_tests` e `create_commit`/`create_pull_request` **continuam simulados**, de propósito: o único runner disponível nesta máquina (`LocalProcessSandboxRunner`, `@forge/sandbox`, Fase 8) não isola rede — rodar um comando real a partir de uma proposta de IA exigiria `DockerSandboxRunner` com `--network=none` (ou equivalente), indisponível sem Docker aqui. Conectar isso é a lacuna que resta (ver abaixo).
- Path safety reaproveita `resolveInsideWorkspace` (`@forge/sandbox/path-policy.ts`) — a mesma função que `LocalProcessSandboxRunner` já usava para validar `cwd` de `run_command`, agora também importada por `apps/api` (nova dependência `@forge/sandbox` do app) para validar o `path` proposto de cada escrita.
- Aplicação de patch reaproveita `diff` (jsdiff, já dependência de `apps/web`/`packages/database`) — o mesmo formato de unified diff mínimo que `packages/ai/src/mock-provider.ts` já produzia (sem cabeçalho `Index:`/`===`), confirmado compatível com `applyPatch` antes de escrever qualquer código.

**Arquitetura**: a lógica de fs real vive em `apps/api/src/modules/agent-runs/agent-run-workspace.service.ts` (`AgentRunWorkspaceService`), não em `@forge/agents` — mesma decisão de design de `RepositoryFsService`/`ArtifactStorageService` (fs real por trás de um serviço Nest em `apps/api`, nunca em um pacote framework-agnostic). Preserva intocada a garantia já testada de `AgentRunOrchestrator` ("`require_approval` NUNCA executa de verdade" — ver `orchestrator.test.ts`): o orquestrador continua gravando só o resultado simulado; a execução real acontece inteiramente em `AgentRunsService.decide()` (chamado por `approve()`/`reject()`), ANTES de qualquer transição de status ser persistida.

**Falha real de patch = execução vai para `failed`, mesmo tendo sido aprovada**: se `applyPatch` não aplicar limpo (ex.: outra execução já alterou o arquivo desde então), a aprovação não "funciona" silenciosamente — `AgentRunsService.decide` computa o status final (`completed` vs `failed`) SÓ DEPOIS de tentar as escritas reais, não antes. A linha de `approvals` continua registrando a decisão HUMANA como `approved` (o tech lead realmente aprovou); é o status da EXECUÇÃO que diverge para `failed` pela falha técnica real — as duas coisas são conceitos distintos e ficam em colunas/tabelas distintas de propósito, sem inventar um terceiro valor no enum `AgentRunStatus`/`ApprovalStatus`.

Audit log novo: `agent_run.changes_applied` (além do já existente `agent_run.approved`/`agent_run.rejected`), emitido só quando pelo menos uma tool call de escrita foi processada de verdade — metadata lista `{ toolCallId, path, ok, error? }` por escrita, nunca conteúdo de arquivo/patch.

## Fase 14 continuação — OpenTelemetry real (traces)

Implementado nesta sessão: a lacuna explícita registrada desde a criação da Fase 14 ("Sem OpenTelemetry real") — o "trace sink" de aplicação já existente (`AgentRunTraceEvent`/`AgentRunTraceSink`, `packages/agents/src/ports.ts`, consumido por `AgentRunTraceLoggerService`) agora também alimenta spans OTel reais e exportáveis, além do log estruturado condicionado a `FORGE_TRACE_LOGS=1` (que continua existindo, inalterado).

**SDK e bootstrap** (`apps/api/src/tracing.ts`, `@opentelemetry/sdk-node` + `@opentelemetry/auto-instrumentations-node`, que cobre HTTP/Express por baixo do NestJS automaticamente): mesma filosofia de PGlite/fila em memória/IA mock — funciona local sem nenhuma credencial (`ConsoleSpanExporter`, `SimpleSpanProcessor`, um span por linha assim que termina) e só exporta para um backend real (`@opentelemetry/exporter-trace-otlp-http`, com `BatchSpanProcessor`) quando `OTEL_EXPORTER_OTLP_ENDPOINT` está definido — opt-in via env var, nunca exigido. `tracing.ts` é importado como a primeiríssima linha de `main.ts` (antes até de `@nestjs/core`): em módulos ES (`apps/api` é `"type": "module"`), a especificação garante que imports estáticos de módulos irmãos sem dependência entre si são avaliados na ordem em que aparecem no arquivo, então isso basta para a auto-instrumentação corrigir (patch) `http`/`express` antes de o NestJS criar o servidor real — não foi preciso `--import`/`-r` no `node`.

**Ponte para o trace sink de agentes** (`apps/api/src/modules/agent-runs/agent-run-otel-span-recorder.ts`, `AgentRunOtelSpanRecorder`, injetado em `AgentRunTraceLoggerService`): cada evento `agent.step` (start/end) abre/fecha um span raiz nomeado `agent.step <role>`; cada evento `tool.call` (start/end) abre/fecha um span filho do step em que ocorreu, localizado via um `Map` de spans de step ainda abertos e propagado com `trace.setSpan(context.active(), parentStep)`. `packages/agents` continua desacoplado de OpenTelemetry de propósito (só conhece a porta mínima em `ports.ts`) — toda a ponte para OTel vive em `apps/api`, mesmo ponto que já hospedava o sink original. Todo atributo de span que vem de `event.attributes` passa por `redactSensitiveValues()` (a mesma função que já protegia os logs estruturados) antes de virar atributo — defesa em profundidade, já que o contrato atual de `AgentRunTraceEvent` só carrega metadados leves (não `arguments`/`result` brutos de tool call), mas um evento futuro poderia mudar isso.

**Lacuna deliberada, não esquecida**: não existe um span raiz agregador único por `agentRun` inteiro (englobando todos os steps de uma execução) — a porta `AgentRunTraceEvent` não expõe um evento de início/fim da execução completa, só de cada step/tool call. Abrir isso exigiria mudar o contrato de `ports.ts` (fora do escopo mínimo desta continuação, que era ligar a fundação real de HTTP + execução de agente). Também não há instrumentação retroativa de tudo (ex. queries Drizzle individuais não ganham span próprio hoje, só o span HTTP que as envolve) — ver "O que falta" abaixo.

## Fase 14 continuação #3 — propagação de trace context web/API

Implementado nesta sessão, a partir da lacuna registrada na tabela de fases e em "O que falta" ("propagação de trace context entre `apps/web` e `apps/api` — cada requisição do proxy Next.js hoje inicia um trace novo, sem `traceparent` herdado"). Antes desta continuação, `apps/api/src/tracing.ts` (Fase 14 continuação) já emitia spans OTel reais para toda requisição HTTP recebida, mas o proxy same-origin de `apps/web` (`/api/:path*`, `next.config.ts` `rewrites()`) nunca gerava nem propagava um `traceparent` W3C — cada requisição chegava "fria" na API, que iniciava um trace novo e desconectado de qualquer coisa do lado do Next.js.

**Decisão de escopo (avaliada antes de implementar, não a primeira ideia testada)**: instrumentar `apps/web` inteiro com `@opentelemetry/auto-instrumentations-node` (o mesmo pacote que `apps/api` usa) cobriria toda requisição de página/RSC/asset, não só o proxy — um projeto maior, com risco real de instabilidade/overhead que não se justifica para o gap real (só a ponte `/api/*` -> `apps/api` precisa propagar contexto; o resto do Next.js nunca teve, nem precisa ter, um trace próprio). A solução implementada é deliberadamente mínima: `apps/web/src/tracing.ts` (novo) cria só um `TracerProvider` mínimo (`BasicTracerProvider`, `@opentelemetry/sdk-trace-base` — o mesmo pacote que `agent-run-otel-span-recorder.spec.ts` já usa em `apps/api` para testar instrumentação manual, comprovadamente resolvível neste ambiente pnpm) e `apps/web/src/proxy.ts` cria manualmente UM span CLIENT real por requisição que bate no rewrite `/api/:path*` — nunca um span "fake"/log disfarçado de span, nunca auto-instrumentação de todo o Next.js.

**Mesma filosofia de zero-credencial do resto do projeto**: `ConsoleSpanExporter` por padrão (span real impresso no stdout do processo do Next.js assim que termina, igual `apps/api/src/tracing.ts`); `OTLPTraceExporter` opt-in só quando `OTEL_EXPORTER_OTLP_ENDPOINT` está definido — mesmo par de dependências novas de `apps/api` adicionado a `apps/web/package.json` (`@opentelemetry/api`, `@opentelemetry/core`, `@opentelemetry/exporter-trace-otlp-http`, `@opentelemetry/resources`, `@opentelemetry/sdk-trace-base`, `@opentelemetry/semantic-conventions`).

**Por que dá para rodar OTel dentro de `proxy.ts`**: desde o Next.js 16, "Proxy" (renome de `middleware`) roda por padrão no runtime Node.js completo (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`, seção "Runtime": "Proxy defaults to using the Node.js runtime") — confirmado lendo a doc local antes de assumir, não por suposição. Não há restrição de Edge runtime aqui, então pacotes Node normais funcionam sem adaptação.

**Como o header chega em `apps/api` sem nenhuma mudança do lado da API**: `buildProxyTraceHeaders()` (`apps/web/src/tracing.ts`) extrai um `traceparent`/`tracestate` de entrada se houver (nunca existe vindo do browser hoje — nenhuma instrumentação client-side foi adicionada, fora de escopo; o browser nunca teve um trace pra herdar, então é honesto que o primeiro hop real com um trace seja o proxy de `apps/web`), abre e fecha um span CLIENT real, e injeta o contexto resultante (via uma instância local de `W3CTraceContextPropagator`, `@opentelemetry/core` — deliberadamente NÃO usando `propagation.extract`/`inject` globais de `@opentelemetry/api`, que exigiriam registrar um propagador global só para uso interno deste módulo) como headers na requisição que segue para `NextResponse.next({ request: { headers } })`. Next.js propaga esses headers (documentado em "Setting Headers" da doc de Proxy) para a requisição que o rewrite de `next.config.ts` de fato encaminha para `apps/api`. Do lado da API, **nenhuma mudança de código foi necessária**: confirmado lendo o código-fonte de `@opentelemetry/instrumentation-http` (`http.js`, linha ~344: `const ctx = api_1.propagation.extract(api_1.ROOT_CONTEXT, headers);`) que a auto-instrumentação HTTP já extrai o `traceparent` de toda requisição recebida usando o propagador GLOBAL, e lendo `@opentelemetry/sdk-node` (`utils.js`, `setupPropagator`) que `NodeSDK.start()` (chamado em `apps/api/src/tracing.ts` sem nenhuma opção de propagador) já registra esse propagador global como `CompositePropagator([W3CTraceContextPropagator, W3CBaggagePropagator])` por padrão — ou seja, a API já honrava um `traceparent` de entrada desde a Fase 14 continuação original, só nunca tinha recebido um de verdade.

**Verificação real (não por autorrelato), dois processos Node reais**: `apps/api/test/otel-trace-propagation.e2e-spec.ts` (novo) sobe `node dist/main.js` (API real) e `next dev -p <porta>` (Next.js real, invocado direto via `node .../next/dist/bin/next`, mesmo padrão de invocar `nest.js` direto nos specs vizinhos) como dois processos filhos reais, faz duas requisições HTTP reais e independentes via `GET /api/auth/me` através do proxy same-origin (sem cookie de sessão — 401, irrelevante para a asserção, já que a auto-instrumentação HTTP cria o span ANTES de qualquer guard decidir o status), e inspeciona o `stdout` bruto capturado dos dois processos: o `traceId` (32 hex chars) do span CLIENT impresso pelo Next.js é o MESMO `traceId` do span HTTP SERVER impresso pela API, para cada uma das duas requisições — e os `traceId`s das duas requisições são diferentes entre si (prova negativa de que não é um valor fixo/hardcoded). ## Fase 11 continuação #2 — decisão de aprovação de deployment (queued -> approve/reject)

Implementado nesta sessão: a lacuna registrada na tabela acima ("decisão approve/reject do gate... pendentes") — até aqui um `deployment` protegido ficava `queued` com uma `approval` `pending` para sempre, sem nenhum jeito de decidi-la. `POST /projects/:projectId/environments/:environmentId/deployments/:deploymentId/approve` e `.../reject` (`apps/api/src/modules/environments/environments.controller.ts`/`.service.ts`/`.repository.ts`) resolvem isso, seguindo o mesmo padrão já validado por `AgentRunsService.approve`/`reject`/`decide` (Fase 17): 409 se o `deployment` não estiver `queued` ou não houver uma `approval` `pending` para ele, 404 genérico cross-tenant (projeto/ambiente/deployment fora do tenant), audit log `deployment.approved`/`deployment.rejected`.

**Decisão de permissão (a parte não óbvia do briefing) — `environment:approve_deployment` é uma permissão NOVA, não reaproveita `environment:deploy`**: hoje `environment:deploy` (quem pode SOLICITAR um deploy) só é concedida a `platform_engineer`/`admin` — ao contrário do fluxo de `agent_run`, onde `agent_run:trigger` já tem um conjunto de papéis mais amplo (developer/qa_engineer/tech_lead/platform_engineer) do que `agent_run:approve` (tech_lead/platform_engineer/admin). Se a decisão de aprovar um deployment reaproveitasse `environment:deploy`, o único papel não-admin capaz de solicitar (`platform_engineer`) também seria o único capaz de aprovar o próprio pedido — esvaziando o sentido do gate (spec §13: "Deploy para ambientes protegidos exige aprovação" pressupõe um segundo julgamento humano, não o mesmo ator). Por isso `environment:approve_deployment` (`packages/types/src/enums.ts`, `packages/domain/src/permissions.ts`) fica restrita só a `admin` — estritamente mais restrita do que quem solicita, não o mesmo conjunto de papéis. Isso exigiu adicionar um usuário demo novo: `admin@acme-platform.example` / `demo1234` (`packages/database/src/seed/run-seed.ts`, `ensureDemoAdmin`), já que antes desta sessão não havia nenhum usuário `admin` seedado na organização "Acme Platform".

**Decisão sobre SSE vs. refetch simples**: ao contrário do fluxo de `agent_run` (que tem uma página de detalhe dedicada por execução, com `AgentRunEventsService`/SSE), deployments não têm uma view de "detalhe ao vivo" — só um badge numa lista na tela de projeto (`project-detail-view.tsx`). A decisão em si é uma única chamada HTTP síncrona que já retorna o estado final (não há um processo assíncrono rodando em background para acompanhar depois da resposta). Por isso esta sessão optou por **não** adicionar um canal SSE aqui: o mesmo padrão de invalidação de query do TanStack Query que `requestDeployment` já usava (`queryClient.invalidateQueries(['projects', projectId, 'environments'])` após a mutação) já satisfaz o requisito de "refletir o resultado sem reload manual da página inteira" sem a complexidade adicional de mais um canal de eventos para um resultado que não muda depois de decidido.

**Reaproveitamento da tabela `approvals`, mas com uma diferença real do padrão de `agent_run`**: o fluxo de `agent_run` (Fase 17) insere uma linha JÁ DECIDIDA em `approvals` no momento da decisão, porque não existe hoje um registro `pending` prévio naquele fluxo. Deployments são diferentes: `requestDeployment` (Fase 11 original) já grava a `approval` em `pending` no momento do pedido (`createPendingDeploymentApproval`) — então decidir aqui é um UPDATE na MESMA linha (`EnvironmentsRepository.decideDeploymentApproval`), preenchendo `approvedByUserId`/`decidedAt`, não um INSERT de uma linha nova. `reason`: se quem decide informar um motivo, ele substitui o motivo original (a justificativa automática do pedido); se não informar, o motivo original é preservado — é a mesma coluna para os dois casos, não há campo separado.

Aprovação conclui o `deployment` como `succeeded` (mesma simulação demo de "sucesso imediato" que ambientes não-protegidos já tinham, com `startedAt`/`completedAt` reais); rejeição conclui como `failed` — sem estado "cancelado" à parte (`DeploymentStatus` não tem um, ao contrário de `AgentRunStatus`), a diferença entre "erro técnico" e "rejeitado por um humano" fica na linha de `approvals`/audit log, não no enum de status (mesmo raciocínio já usado na Fase 17 para `agent_run`).

Frontend: `apps/web/src/app/(product)/projects/[id]/project-detail-view.tsx` ganhou botões "Aprovar deploy"/"Rejeitar deploy" no card de cada ambiente quando há gate pendente, visíveis só para quem tem `environment:approve_deployment` no cliente (`apps/web/src/lib/deployment-approval-permission.ts`, mirror do RBAC do backend, mesmo padrão de `agent-run-approval-permission.ts`). ## Convenções estabelecidas (leia antes de escrever código novo)

- **Sem build step** em `packages/types`, `packages/domain`, `packages/database`, `packages/ai`, `packages/agents`: imports relativos internos usam extensão `.ts` explícita (não `.js`) — Node nativo em modo strip-only exige apontar pro arquivo que existe de verdade em disco. **Sempre valide `apps/api` como processo real** depois de mexer nesses pacotes (`apps/api/test/runtime-smoke.e2e-spec.ts`) — typecheck/Vitest sozinhos mascaram esse tipo de bug.
- **Infra local sem credenciais externas**: PGlite no lugar de Postgres, fila em memória no lugar de Redis, IA mock no lugar de Anthropic real. Trocável via env var sem mudar código.
- **Todo endpoint novo**: `*Repository` com `organizationId` no `WHERE`, `*Service` fino, `*Controller` com guards + `@RequirePermission`, 404 genérico cross-tenant.
- **Todo teste novo é real**: PGlite de verdade, supertest real, Playwright com servidores reais.
- **Bancos de e2e fixos em disco** (`apps/web/.data/e2e-web/`) precisam ser resetados a cada execução da suíte — ver `apps/web/e2e/reset-e2e-db.mjs`. Se criar outra suíte e2e com banco próprio, replique esse padrão.
- **Processo de trabalho validado**: cada fase/tarefa grande = um agente em background com briefing detalhado e critério de aceite com verificação real. Ao terminar, **sempre reverificar de forma independente** antes de confiar (rebuild sem cache, e2e completo, ler código dos pontos sensíveis) — isso já pegou várias regressões reais que o autorrelato não via.
- Se um agente falhar com `rate_limit`/429, retome com `SendMessage` usando o `agentId` (preserva contexto) em vez de recomeçar.
- Pode haver uma **sessão paralela de outro projeto** nesta máquina usando portas 3000-3002/5183 — nunca mate processos que não sejam do Forge; use portas 3100+ para testes.
- **Se outra ferramenta de IA estiver/tiver trabalhado no mesmo repo em paralelo**, `git status --short` primeiro, sempre.
